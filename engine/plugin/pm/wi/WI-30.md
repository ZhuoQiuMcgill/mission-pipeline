# WI-30 A leaf is missing or was edited by hand, or a commit the memory names is not reachable here

## Trigger and evidence
- A leaf the memory refers to (a Markdown file under `.mission-pipeline/`) is missing, or its text no longer matches the hash recorded with it: "leaf missing", "leaf edited after it was recorded".
- A commit the memory names, with the objects it needs, is not in this repository: "commit not reachable here" (e.g. a copy of the folder next to a repository that lacks those commits).
- Found after a copy or move, or when a read or a step needs that leaf or commit.
- Evidence: the node, the file and anchor, the recorded and the current hash; the commit and the missing objects.

## Default action already taken
The memory keeps working: the node is shown with the mark. Only the steps that need that content are held: delivering that commit, continuing a task on it, a card that must quote that leaf. Everything else goes on.

## Options and outcomes
1. Restore the content: put the leaf back from the source copy, or undo the hand edit; fetch the missing commits into the repository (the user runs the git command, e.g. `git fetch` from the source repository) → the next check finds them and the held steps are ready again.
2. A leaf edited on purpose (a correction): the edit stays, shown as edited; the recorded hash still names the original. If the edit changes meaning, record the change the proper way (a new requirement item version, a PM plan batch).
3. The content is gone for good: redo the work that needs it (dispatch the step again, or a PM plan batch); the old node stays marked.

## How to choose
A copy that left something behind → 1. A hand edit → find out who made it: a correction → 2; a change of meaning → 2 with the proper record. Code that exists only on another machine → 1, or 3 when that machine is gone.

## When to ask the user
When the edited leaf is the user's words (`words/…`) or a decision: only the user can say whether the edit stands. When the missing commits are where only the user can reach them.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
