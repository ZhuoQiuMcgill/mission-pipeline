# WI-27 A web fetch was refused

## Trigger and evidence
- A seat's web fetch was refused: the address, or a redirect, is outside the card's allow list; the address is not public (a private, loopback or link-local address); or the ledger did not authorize the network action.
- Evidence: the address and the redirect chain, the card's allow list, the refusal reason.

## Default action already taken
The fetch is refused and nothing is fetched; the seat's round continues with the answer "not obtained".

## Options and outcomes
1. The address is needed: add it to the card's allow list and rerun the round (through the Secretary; no `mp` command yet: state the choice in the session) → counted as a restart (6.5).
2. Accept "not obtained" → the round goes on without it; the seat says what it could not read.

## How to choose
The address is a legitimate source the task needs → 1; a redirect to an unexpected host, or a non-public address → 2 (never widen the allow list for those).

## When to ask the user
When the address is the user's own system or the source matters to what the user gets.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
