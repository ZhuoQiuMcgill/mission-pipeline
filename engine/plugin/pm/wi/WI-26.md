# WI-26 A decision-layer step cannot continue as it is

## Trigger and evidence
- A decision-layer seat's attempt (Calibrator ①, the Architect's decomposition or feasibility, Calibrator ②) ended in a state the program must not repair by itself; typically its result was quarantined because of a stop (6.4: never restarted while the stop holds). The step has no other option.
- Evidence: the task, its disposition and note, the stop.

## Default action already taken
Only this plan step waits. The rest of the mission (tasks of an earlier effective plan, explorations) goes on within the stop's scope. Nothing restarts automatically.

## Options and outcomes
1. The stop was meant (the user stopped this work): leave it → the plan stays where it is until the user wants to continue.
2. The stop is released and the work should go on: submit a new PM batch (the same plan is fine): `mp plan submit <mission> --file <plan.json>` → the decision layer runs again from Calibrator ①; accepted work is not redone; loop counts are kept per PM plan version.
3. The stop is still active but too wide: narrow it with the user (`mp stop-narrow <stop> --scope ...`), then 2.

## How to choose
The user said stop → 1 until the user says otherwise; a stop that was too wide (e.g. "no network" also caught this seat) → 3.

## When to ask the user
Always before resuming work the user stopped (the stop is the user's).

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
