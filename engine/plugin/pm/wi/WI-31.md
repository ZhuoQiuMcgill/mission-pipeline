# WI-31 The repository lives outside the folder, a copy shares one repository with another copy, or a copy's worktree links cannot be verified

The Secretary handles this page.
For an existing escalation, route a PM-class choice with `needs-pm` / `ask-pm` through `mp sec decide <escalation> ...`.
For a question without an escalation, use `mp sec ask-pm "<question>" [--about <notice or item id>]`; the PM answers with `mp pm reply <id> "<text>" [--words W-n]`, visible in `mp sec next` / `mp sec wait`.
The PM decides on recorded words or asks the user under F-3; the PM runs the words-dependent `mp pm` actions below.

## Trigger and evidence

- At `mp init`, or after a move, `mp` found that the git directory or its common directory lies outside the project folder (a linked worktree, a shared repository), or the repository uses alternates, or it is a partial clone. A copy of the folder then carries the memory but not necessarily the code, and two copies on one machine share one repository.
- After a move, with the git common directory outside the folder: this copy shares its repository with the original.
- Evidence: the git directory and common directory, the alternates, the partial clone.

- If copied worktree links cannot be verified after repair, git writes stay held and the move stays pending: correct the copied `.git`/`gitdir` links and `commondir`, then retry `mp`. While link verification is pending, `confirm-copy` is refused without appending an event or releasing the hold. Registrations whose worktree `.git` is absent in the copy are prunable: they are skipped and reported in the move findings.

## Default action already taken

At `mp init`: a warning only; it still initializes and never rewrites the repository. After a move into a shared repository: `mp` skipped `git worktree repair`, rewrote nothing in the repository, and holds every command that writes to git (dispatching a Constructor, a hand-back that commits, a delivery, a landing) until you confirm that this copy is the one in use. Reads and steps that do not write to git go on.

## Options and outcomes

1. This copy is the one in use from now on, and the other copy will not be used: `mp pm confirm-copy` → git writes are allowed again in this copy.
2. Keep using the other copy: stop using this one; nothing changes.
3. Make this copy standalone: the user makes a standalone clone of the repository for it, then 1.
4. At init (the warning only): nothing to do; remember that copying the folder does not carry the code.

## How to choose

Two copies must never both write to one repository: they would move the same refs and worktrees. One copy in use → 1; both needed → 3, then 1.

## When to send to the PM

Use the escalation's `ask-pm` option if it has one; otherwise record the question with `mp sec ask-pm "<question>" --about <notice or item id>`. The PM decides on the words or asks the user.
Before 1 unless the PM's recorded instruction already establishes which copy is in use; the PM decides from those words or asks the user.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
