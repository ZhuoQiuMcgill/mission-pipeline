# WI-18 The startup self-check failed, or a platform capability is missing

## Trigger and evidence
- Any startup self-check item failed (after install, after upgrading Claude Code, the SDK or Node, or at a start); at install, cgroup v2 does not delegate memory, pids and cpu to the user, or bubblewrap cannot run.
- Evidence: failed items, raw events and exit statuses, versions tested.

## Default action already taken
Any of items 1–8 and 10 failed: on platforms that need full isolation no seat starts; queries, stops, cleanup and landing of accepted deliveries go on. Only item 9 failed: only `unlimited` spending is offered; seats start. No cgroups: no "run command" and no program verification runs unless the user accepts the "resource-limits" degradation.

The self-check (offline items and live items 1–3 and 8) runs by itself: at `mp install`, and in the background when the engine starts and the versions changed (a Claude Code, SDK or Node update), at most once an hour per set of versions. A failed run raises one notice naming the failing items.

## Options and outcomes
1. Run it again now: `mp selfcheck` (prints each item; exit 0 when it passed) → seats start as soon as it passes; nothing else is needed.
2. Go back to the last set of versions that passed → seats start again; the new versions' features wait.
3. Fix the environment (delegate cgroups, install bubblewrap, log in to Claude Code again; the user runs what needs administrator rights), then `mp selfcheck` (or `mp install`) → seats start once the self-check passes.
4. A degraded mode the platform allows, only after the user explicitly accepts it: `mp install --accept-degradation resource-limits` (or isolation, host-write-cap).

## How to choose
A live item failed once (the model service or the login was briefly unavailable) → 1; it failed only after an upgrade → 2; the environment changed → 3; the platform cannot do it at all → 4.

## When to ask the user
When administrator rights are needed, or to enable a degraded mode (a safety trade-off: the user decides).

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
