# WI-04 A worktree does not match the delivery after landing

The Secretary handles this page.
A choice needing the user's words or a PM-class decision goes to the PM inbox: use `needs-pm` / `ask-pm` on the escalation with `mp sec decide <escalation> ...`.
The PM decides on recorded words or asks the user under F-3; the PM runs the words-dependent `mp pm` actions below.

## Trigger and evidence

- After a landing, or when a call finds an open landing done (WI-06), the worktree holding the target branch does not match the delivery commit: "branch advanced, files stale", "looks like a reverse change", or "cannot determine". Usual cause: someone ran git or edited files in that worktree during the landing.
- Evidence: worktree, HEAD, index-versus-files comparison, differing paths. Unlike the pre-landing check (WI-02), eol/ident normalization applies only where both the blob and conversion are unchanged from the base. A changed blob or conversion needs the delivery's exact checkout bytes. Untouched LF files under `core.autocrlf=true` may still match.

## Default action already taken

The landing is recorded as done (the branch is at the delivery commit). The worktree is not touched; `mp read status` keeps showing it.

## Options and outcomes

1. Run the git command the notice gives (given only when its precondition held at the check) → index and files move from the base to the delivery commit, keeping non-conflicting local changes; on a conflict git refuses and changes nothing; then 3.
2. A disposable temporary worktree (a finished agent's): its owner decides whether to remove it (`git worktree remove` deletes ignored files: list them first). You never remove it yourself.
3. Give an authorized agent the differences and explanation for a manual merge; send a choice needing the user to the PM.
4. A reverse commit already exists: revert it as the notice explains; the delivery commit itself is never lost.

## How to choose

The precondition held → 1; a temporary worktree → 2; otherwise → 3 or 4.

## When to send to the PM

Use `ask-pm` for the cases below; the PM decides on the words or asks the user.
When that worktree is the user's own.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
