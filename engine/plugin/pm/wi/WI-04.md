# WI-04 A worktree is inconsistent with the delivery after landing

## Trigger and evidence
- The post-landing scan or check classifies a worktree as "branch advanced, files stale", "looks like a reverse change", or "cannot determine". Causes include the concurrent operations of risks 18, 26, 27, or running out of space.
- Evidence: worktree, HEAD, index-versus-files comparison, differing paths.

## Default action already taken
The worktree is not touched; layer 0 keeps showing it; the PM is told.

## Options and outcomes
1. Run the recovery command (given only when a re-check right before the report confirms its precondition; see the notice's facts) → index and files move from the base to the delivery commit, keeping non-conflicting local changes; on a conflict it refuses and changes nothing; go to 3.
2. A disposable temporary worktree (e.g. an agent's, finished): its user decides whether to remove it (`git worktree remove` deletes ignored files; the PM lists them first; the PM never removes it).
3. Merge by hand: the PM gives the differences and an explanation; the user or an agent does it.
4. A reverse commit already exists: revert it as the notice explains; the delivery commit itself is never lost.

## How to choose
Precondition holds → 1; temporary worktree → 2; otherwise → 3 or 4.

## When to ask the user
When that worktree is the user's own.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
