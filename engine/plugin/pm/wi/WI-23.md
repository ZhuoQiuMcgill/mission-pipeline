# WI-23 A re-plan dropped or changed a task that has work in flight

## Trigger and evidence
- A new detailed plan took effect (after Calibrator ②, or a Secretary or user ruling) while a Constructor or Reviewer of one of its tasks was running, and the new plan drops that task or changes its card (goal, standards, write scope, commands).
- Evidence: the task, the attempt, the running launches, the old and new plan versions.

## Default action already taken
The running seats finish; their results are recorded but not continued under the old card. Queued attempts of the old card are cancelled. A changed task starts its next attempt with the new card in the same lineage (its loop counts go on). A dropped task stops and keeps its products: nothing is deleted. The rest of the mission goes on.

## Options and outcomes
1. Let it be (default) → the finished attempt's product stays in the ledger as an unaccepted or old-card version and is not delivered.
2. The dropped work was worth keeping: have the Architect re-plan with it (the Secretary's "re-plan" on a related task, or a new PM batch saying so: `mp plan submit <mission> --file <plan.json>`) → the task comes back with a card that matches the work done; its next attempt reworks from it.
3. The change was a mistake: submit a PM batch that restores the old element (`mp plan submit <mission> --file <plan.json>`) → the decision layer re-plans and the task's card goes back at the next attempt.

## How to choose
The task was dropped on purpose (the user changed scope) → 1; expensive work in flight that the new plan could have used → 2; the re-plan misread the user → 3.

## When to ask the user
Only when the drop changes what the user gets (3.2 kind 1); the user should already have seen it at Calibrator ①.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
