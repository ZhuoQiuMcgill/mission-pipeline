# WI-23 A re-plan dropped or changed a task that has work in flight

## Trigger and evidence
- A new detailed plan took effect (after Calibrator ②, or a Secretary or user ruling) while a dispatch of one of its tasks (Constructor, Reviewer) was in flight, and the new plan drops that task or changes its card (goal, standards, write scope, commands).
- The same notice when a task is abandoned, or, at the first passes after an upgrade to 4.1.1, when a dependent attempt dispatched by 4.1.0 is restarted on a pinned start ("restarted for legacy prerequisite pins") while its seat runs.
- Evidence: the task, the dispatches in flight, the old and new plan versions.

## Default action already taken
The dispatches in flight may finish: their hand-backs are recorded but not continued under the old card. Ready steps of the old card are withdrawn from `mp pm next`. A changed task's next attempt gets the new card in the same lineage (its loop counts go on) and starts from its dependencies' current work, without the earlier attempts' change (that work stays readable at its commit). A restarted legacy attempt carries the task's latest recorded product instead. A dropped task stops and keeps its products: nothing is deleted. The rest of the mission goes on.

## Options and outcomes
1. Let it be (default) → the finished work stays in the memory as an unaccepted or old-card version and is not delivered. To save effort, you may stop those seats in your harness and release them (`mp pm release <id> --ended`).
2. The dropped work was worth keeping: have the Architect re-plan with it (a PM plan batch saying so: `mp pm plan submit <mission> --file <plan.json> --words W-<n>`) → the task comes back with a card that matches the work done.
3. The change was a mistake: submit a PM plan batch that restores the old element → the decision layer re-plans and the task's card goes back at the next attempt.

## How to choose
Dropped on purpose (the user changed scope) → 1; expensive work in flight that the new plan could have used → 2; the re-plan misread the user → 3.

## When to ask the user
Only when the drop changes what the user gets; the user should already have seen it at Calibrator ①.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
