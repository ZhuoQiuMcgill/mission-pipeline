# WI-20 Inconsistent program records, a changed program namespace, or an internal error

The Secretary handles this page.
A choice needing the user's words or a PM-class decision goes to the PM inbox: use `needs-pm` / `ask-pm` on the escalation with `mp sec decide <escalation> ...`.
The PM decides on recorded words or asks the user under F-3; the PM runs the words-dependent `mp pm` actions below.

## Trigger and evidence

- A ref under `refs/mission-pipeline/` exists but points to another commit than the memory records; the same operation id came with different content; `mp` ended on an internal error (an unexpected exception); or the stored labels disagree with a recomputation.
- Evidence: the ref and both commits; both versions of the operation; the error message.

## Default action already taken

Only the operation concerned stops: the ref is not rewritten, the conflicting write is refused, existing records are unchanged. Everything else goes on.

## Options and outcomes

1. An outside change (an agent or tool moved a ref in the program's namespace) → deliver again under a new operation id (`mp pm deliver ... --op <new id>`); `mp` never overwrites an existing ref.
2. Labels that look wrong: `mp recompute` → the derived tables are rebuilt from the base records.
3. A suspected defect of Mission Pipeline (an internal error, the same failure at the same place again) → send the facts to the PM, with the evidence, so it can be reported; retry after a fixed version of `mp` is installed.

## How to choose

Traces of an outside change → 1; only labels in doubt → 2; neither → 3.

## When to send to the PM

Use `ask-pm` for the cases below; the PM decides on the words or asks the user.
For a suspected defect, or when someone changed the program namespace on purpose.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
