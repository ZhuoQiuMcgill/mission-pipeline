# WI-20 An inconsistency in program records or the program namespace, or a program internal error

## Trigger and evidence
- At recovery a ref in the program's namespace exists but points to another commit; a termination proof does not match its launch id, is malformed, or the same launch has a different proof (including proof files marked "rejected"); the same identity was submitted with different content; a program internal error (an unexpected exception, v51).
- Evidence: ref name and both commits; the proof and the registered one; both versions of the fact; the error message.

## Default action already taken
Only the operation or attempt concerned stops: the ref is not redone and completion is not recorded, the delivery stays "to be verified"; rejected proof files go to a quarantine directory; the attempt goes through proof reconciliation (re-dispatched and counted per WI-15 when needed); conflicting facts are refused, existing ones unchanged. Everything else goes on.

## Options and outcomes
1. Find the source: an external tool or agent changed the program's namespace → record the outside value as a fact and deliver again under a new operation id (`mp deliver ... --op <new id>`; the program never overwrites an existing ref).
2. Looks like a program defect (two proofs for one launch, an internal error) → tell the maintainer with the evidence; the affected attempt is redone as an environment failure.

## How to choose
Traces of an outside change → 1; none → 2.

## When to ask the user
For a suspected program defect, or when someone changed the program namespace on purpose.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
