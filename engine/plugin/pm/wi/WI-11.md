# WI-11 The evaluator is in its fault state, or its resource pool is too small

## Trigger and evidence
- The derived state cannot be computed: 3 failures since the last successful publication, and one rebuild from scratch also failed; or a periodic re-measurement finds the evaluator's pool too small.
- Evidence: failure reasons and count, the last checkpoint's revision, the pool's measured need and current size.

## Default action already taken
Fault: the evaluator is not restarted again; reads return the last checkpoint's summary and how far it lags (`mp status`); operations that need "proven" (stable dispatch, legalization stamps, objects delivered as proven, full-close) end with that reason; everything else goes on. Pool too small: checkpoints pause; evaluation goes on.

## Options and outcomes
1. Retry: `mp retry-evaluator` → the failure count is cleared and the evaluator restarts; operations ended for this reason are registered again by the program after the next successful publication.
2. Enlarge the evaluator's pool within the machine's capacity (for now: edit the evaluator settings in scheduler.json, then `mp retry-evaluator`); beyond the machine's capacity, WI-10.
3. Go on in fast mode for now → results are marked not fully proven.
4. A program defect (always fails at the same revision, unrelated to resources) → tell the maintainer with the failure evidence; retry after the fixed version is installed.

## How to choose
Timeouts or memory limits after a large ledger growth → 2; occasional → 1; the same cause a second time → 4, do not keep retrying.

## When to ask the user
When the whole machine needs more capacity (WI-10), or for a program defect.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
