# WI-12 Storage fault, a stop not persisted, the recovery pause after a reboot

## Trigger and evidence
- A storage fault of the ledger; the stop entry reported "fast notice sent, but not persisted (pending commit)"; one boot used up the inbox slots; after a reboot, work that could advance by itself.
- Evidence: fault reason; both inboxes' probes, fault records, torn writes and clean-exit records; the startup decision and its basis (`mp recovery-check`).

## Default action already taken
During a storage fault: stops still send fast notices through the control plane and units still react; stops are committed once storage recovers; nothing is dispatched, authorized or accepted. After a reboot: the program first commits every stop in both inboxes, then decides from the evidence to go on or to enter the recovery pause (covering all work that could advance). When it goes on after an abnormal stop (risk 28, option A), the PM also reminds the user: "Any stop sent before the restart that you did not see confirmed as 'persisted' (including ones shown as 'not persisted'): please say it again if you still want it."

## Options and outcomes
1. In the recovery pause, ask the user: "The machine restarted at <time>; stops sent after <start> without a 'persisted' confirmation may not have been recorded. During that time, did you ask to stop or withdraw anything in the PM session or the terminal?"
2. The user says no: `mp resume --answer "<the user's answer>"` → dispatch resumes.
3. The user says yes: `mp resume --answer "<answer>" --stop-words "<what the user wants stopped>"` → the stop is submitted and committed first, then the rest resumes.
4. Also check this session for stop or withdraw words after the last booked user message (`mp recovery-check`); if there are any, submit them with `mp stop "<the words>"`. The session record may be missing too, so this only adds stops; it never decides whether to go on.
5. A stop "not persisted": tell the user to say it again if they still want it.

## How to choose
In the recovery pause there is only one way: stops are the safety floor and only the user knows a lost one. While the user is away, the pause stays; the PM never answers for the user.

## When to ask the user
Always, in the recovery pause.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
