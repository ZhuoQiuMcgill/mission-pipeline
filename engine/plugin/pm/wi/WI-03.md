# WI-03 An external worktree or branch changed paths in a mission's write scope

## Trigger and evidence
- At a delivery or a landing, `mp` found an external worktree or branch that changed, relative to the base, paths inside the write scope of a module of a mission in flight (committed or not).
- Evidence: worktree, branch, overlapping paths, inferred origin.

## Default action already taken
Nothing is merged or adopted; the pipeline goes on. External work is seen only once it enters the target branch, as the new base: changes inside a write scope register new product versions and re-acceptance; conflicts become integration tasks. `mp` reads commits only, never another worktree's uncommitted files.

## Options and outcomes
1. Do not merge (default) → each side goes on; merging later may bring integration tasks or re-acceptance.
2. Adopt: have that branch's changes reviewed as an external result against the mission's requirement items and acceptance standards (no `mp` command for this yet) → if it passes it can be delivered as proven; if not, it goes on the risk list.
3. Steer the pipeline around it: have the Architect adjust write scopes or the order of tasks not started yet, with a PM plan batch that asks for it (`mp pm plan submit <mission> --file <plan.json> --words W-<n>`) → fewer conflicts, possibly a later delivery.
4. Ask for the external work to be merged into the target branch first → the pipeline continues on the new base; affected products are re-accepted.

## How to choose
The external work is the user's own, in the same direction → 2 or 4; an experiment or half-done → 1; a large overlap with tasks not started yet → 3.

## When to ask the user
When the external work may contradict what the user said, or when the work to adopt is the user's own.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
