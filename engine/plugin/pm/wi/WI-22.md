# WI-22 The watchdog restarted the ledger service or the scheduler, or restarts are exhausted

## Trigger and evidence
- The watchdog found the ledger service's or scheduler's heartbeat lost, or the process exited, and restarted it; or the restarts within an hour reached the limit (5): "restart-exhausted". Evidence: which service, the reason, restarts this hour, where the log is.

## Default action already taken
Restarted with back-off; after a restart it recovers from the ledger, stops are committed first, units in flight are taken over. When restart-exhausted: no more restarts, one merged notice stays on display; stops still go into the inboxes and send fast notices (committed once the service is back); with the scheduler away, the watchdog ends the processes in a stop's scope.

## Options and outcomes
1. An occasional restart: nothing to do.
2. Restart-exhausted: read the log (logPath in the notice). Resources short → handle per WI-10, then retry; storage trouble → WI-12; a suspected defect (crashes on taking over the same record every time) → tell the maintainer and wait for the fixed version.
3. Retry once: `mp retry-service <ledger|scheduler>` → the count is cleared; the PM has one retry per exhausted episode.
4. After that, only the user decides: `mp retry-service <ledger|scheduler> --by-user`.

## How to choose
The cause is handled → 3; unknown cause or a suspected defect → 2 first.

## When to ask the user
For a suspected program defect, or after the PM's one retry also failed.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no repository hooks or forced rewrites in the user's worktrees; no deletion of the user's data.
