# WI-29 The memory's event chain is broken: all writes are stopped

## Trigger and evidence
- When `mp` opened the folder (after a copy or move, or at any check of the log), the hash chain of the event log in `memory.db` did not verify: an event is missing, changed or out of place. Usual causes: the folder was copied while an `mp` command was writing, or `memory.db` was edited or damaged.
- Evidence: `mp read status` names the last valid event and the first one that fails.

## Default action already taken
Every write is refused: the skeleton itself is in doubt. Reads go on. Nothing in the project's repository is changed.

## Options and outcomes
1. Copy again from the source: copy the whole `.mission-pipeline/` folder again, this time while the source is idle (no `mp` command running, no dispatch in flight) → the new copy opens normally.
2. Continue from the last valid event: `mp pm continue-from <event>` → the log is cut back to that event, the current state and labels are rebuilt from it, and writes resume. What was recorded after that event is no longer in the memory: leaves written for it are dropped as leaves without an entry; commits stay in git, unreferenced.
3. Neither is possible yet: keep reading only, and tell the user which part of the history is in doubt.

## How to choose
The source folder still exists → 1. The source is gone, or only a few events follow the break → read what they were (`mp read status`), then 2; redo what they recorded (say the user's words again with `mp pm say`, dispatch the steps again).

## When to ask the user
Before 2 when the events after the break hold the user's words, decisions or deliveries; otherwise tell the user in one line what was done.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
