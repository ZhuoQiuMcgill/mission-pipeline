# WI-28 A dispatch is interrupted: its seat ended without a hand-back, or nobody knows

## Trigger and evidence
- A dispatch is still "in flight" and its seat is no longer working on it, or you cannot tell: the seat's sub-agent ended or failed without `mp seat <id> handback`; your harness lost it; a new PM session (any harness, any machine) found dispatches in flight from an earlier session; a dispatch has been in flight far longer than its step needs.
- Or: a hand-back arrived from a dispatch that was already released.
- Or: `mp pm next` lists a detached run that ended while its dispatch is in flight (section "Detached runs that ended"). A seat starts such a run with `mp seat <id> rerun <command> --detach`; it runs in a worker process of its own and outlives the seat.
- Evidence: `mp pm next` and `mp read status` list the dispatches in flight with seat, step, filler and age; `mp read chain <dispatch>` shows one.

## Default action already taken
None: `mp` cannot see harness processes, so it never decides that a seat died and never releases a dispatch by itself. The step stays claimed; other work goes on. A hand-back after a release is recorded with its content and marked "after release, not accepted". A detached run goes on when its seat ends; when it ends, `mp pm next` lists it for a dispatch still in flight. A run whose worker is gone is recorded as lost.

## Options and outcomes
1. Wait: the seat may still be working (a long build, a slow model) → it hands back and the step advances.
2. Your harness confirms the seat has ended: `mp pm release <id> --ended` → its worktree is removed, its exclusive-resource leases are freed, and its folder `tmp/<dispatch>/` and the shared checkouts only it held are removed; the step is ready again in `mp pm next`.
3. Not confirmed (the old session is gone, another machine): `mp pm release <id> --abandoned` → the step can be dispatched again at once, in a new worktree; the old worktree and its leases stay held, so a late write of the old seat never reaches the new one. Its folder `tmp/<dispatch>/` and the shared checkouts only it held are removed (a seat still reading one loses it; its late hand-back is not accepted anyway). Run `mp pm release <id> --ended` once you know it has ended.
4. A step waits for an exclusive resource still leased to an abandoned dispatch: make sure the old seat no longer runs, then 2 for it → the lease is freed.
5. A late hand-back: nothing to do; it is kept for reading (`mp read chain <dispatch>`) and changes nothing.
6. A detached run ended while its dispatch is in flight: check your harness. The seat is alive → do nothing: it waits on the run and hands back. The seat is gone → `mp pm release <id> --ended`, then dispatch the step again. The new card lists the run under "Runs already made for this step": a finished run is cited, a running one is waited on, a stopped or lost one can run again. The new seat does not run a finished one again.

## How to choose
A recent dispatch with no sign of trouble → 1. Your harness says the seat ended, or you ended it → 2. A dispatch from a session or machine you cannot see → 3, then 2 once nothing can still run. You cannot dispatch a step again before releasing it: a step is claimed once.

A step that keeps ending without a hand-back: read its card (`mp read chain <dispatch>`). A card that cannot be met (write paths too narrow, a missing input) needs the Architect: a PM plan batch that says so (`mp pm plan submit <mission> --file <plan.json> --words W-<n>`). Otherwise try another filler. Repeated attempts count against the lineage's loop (WI-08).

### Explorations
When the seat was an exploration's author, attacker, Stabilizer or interpreter, the exploration waits at that turn until the step is dispatched again; to end it instead, the decision goes through the Secretary (`mp pm answer ... --option abandon` when the user decides).

When the seat ran a registered attempt of a research exploration (`constructor-experiment` or `researcher-reader`), a run given up is recorded as failed and the exploration goes on without it. If the run failed for a cause outside the method that is gone now (a time limit raised, a tool installed), run the attempt again on the user's words: `mp pm repair <mission> --about <exploration> --words W-<n> --kind <kind> --text "<the user's reason>" --rerun <attempt-id>`. It needs no round, and works until an interpretation is submitted. When the attempt should run under a changed card because the user decided so (a cap lifted, a wider search), that is the user's change: `mp pm repair ... --attempts <attempts.json>` (no round, no review). The older commands `mp pm rerun-attempt` and `mp pm amend-attempts` still work for one release.

A detached run of a registered attempt holds the attempt: a change to it (`--rerun`, `--attempts`) is refused with `DISPATCH_IN_FLIGHT` while the run is running, also after its dispatch was released or handed back. Wait until `mp pm next` lists it as ended, or end it now: SIGTERM to the worker pid the refusal names records it as stopped. A worker found gone is recorded as lost first.

An evidence request queued before 4.1.3 with an absolute working directory still fails at its rerun: release its dispatch and dispatch it again; the seat that asked can ask again with a relative one.

### Detached runs
- Lost: the worker restarted or was killed. If only the worker was killed (for example by the out-of-memory killer), its command's processes may still run: check with `ps` before you run the step again.
- A worker on another host is never marked lost from this machine, and a stop reaches it only when it records its result.
- A harness that kills a seat's whole process tree (a cgroup, a job object) can take the worker with it: it reads as lost; run the step again.
- Outside Linux, liveness is the pid alone; on Windows a stop ends the tree by force, so the cleanup commands do not run.

## When to ask the user
When the dispatch ran on a machine or in a session only the user can see, and only they can say whether it still runs. Otherwise not.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
