# WI-21 A full run at the end failed

## Trigger and evidence
- A full run of the project's full suite at the end of a mission (`mp pm full-run`, the PM's call: D-7) failed on a clean checkout of the delivery candidate.
- Evidence: the full-run marker (the commit and tree, the environment, each command's exit, the failing commands' output tail, the words or authorization it cites), and the run summary.

## Default action already taken
Nothing is blocked: the marker records the failure honestly, and every later delivery and closing snapshot shows it ("full suite last run … on this tree: failed"). Nothing was repaired, rerun or merged by itself.

## Options and outcomes
1. Repair: `mp pm repair <mission> --words W-<n> --kind defect --text "<the user's reason, verbatim>" [--about <task-id>]` (name the task the failing output points at) → the Architect adds or reopens the responsible task (mechanical checks only); once its fix is accepted, `mp pm finish` delivers again; the new tree's status says whether the suite has run on it.
2. Report it to the user and merge anyway on their words: tell the user which commands failed and why it may not matter; if they say to merge, `mp pm finish <mission> --words W-<n>` (or `mp pm land` and `mp pm close` with their words) → it lands with the failure on record; the closing snapshot lists it.
3. Run it again: `mp pm full-run <mission> --words W-<n> --reason "<why another run>"` → for a failure that looks environmental or flaky (a timeout, a missing service); a second failure of the same commands means option 1 or 2.

## How to choose
The failing output points at a task of this mission → 1; the failure is outside what the mission changed, or the user has said they accept it → 2; the output points at the environment, not the code → 3, once.

## When to ask the user
Before option 2 always (merging with a failing suite is the user's decision), and before option 1 when the repair changes what the user asked for. Option 3 needs the user only when they have not delegated full runs to you.

The safety floor is never an option: stops stay in force; nothing unproven is called proven; nothing lands without the user's words; no forced rewrites (reset, forced checkout) in the user's worktrees; no deletion of the user's data.
