# 06 两份问卷

这份文件是工作交接用的笔记，不是产品文档，不要合并进 `main`。

这里保存两份发给现场 PM 的问卷原文。它们的答复整理在 `04-field-data.md`。问卷的用法是：由用户把代码块里的内容整段贴给一个真实项目的 PM 会话。

---

## 问卷一：4.3 现场 PM 调查

- **用途。** 了解 4.3 在真实项目里的规模、Secretary 的裁决、原话的记录、停止、席位的行为、异常、模型和用户最常问的问题。带 ★ 的题最重要。
- **怎么用。** 整段贴给现场的 PM 会话。第 2、5、6 节的很多细节在 Secretary 那边，可以把这三节直接贴给 Secretary，它可以回答问题。【印象】类的题要问经历过这些事的那个会话；新开的 PM 会话只能从记录里答，老会话被压缩过的话印象也可能已经丢了。
- **上次的回答。** 2026-11-27，由一个在 4.3.0 上跑了 21.6 天的项目的 PM 会话回答。它在 `memory.db` 的只读在线备份副本上做 SELECT，没有运行 `mp read status`。第一轮没有问 Secretary；第二轮经用户同意，补了几题的数字，并附上了常驻 Secretary 的第一手答复。
- **一处例外。** "只读查询 memory.db"那一行绕开了"只通过 `mp` 读写"的规矩，是为了拿到统计数字而加的，由用户决定是否保留。上次用户保留了它。另外，现场 PM 提到 `mp read status --no-mark` 不移动游标。

````md
# 给 4.3 现场 PM 的调查问卷

这是一次性的调查，用来指导 Mission Pipeline 下一版的设计，与本项目的需求无关。

## 回答方式
- 只读。不要为了回答而修改记忆、派发席位或改动计划。
- 每题先给结论，再注明来源：【记录】（写出用的命令或条目编号）或【印象】（来自你自己的会话经历）。
- 能给数字就给数字。没有数据就写"没有数据"，不要把估计当作事实。
- `mp read status` 会移动"上次询问"的游标，统计类问题请优先用其他读取命令。
- 你不掌握的现场细节，写"不掌握"即可，不要为此去问 Secretary。
- （可选，由用户决定是否保留此行）统计类问题如果 `mp read` 给不出，允许对 memory.db 做只读的 SELECT 查询，并写明用了什么查询。
- 带 ★ 的题最重要，上下文紧张时先答这些。

## 0. 背景
0.1 引擎版本；使用的 harness，以及 PM、Secretary 和各席位实际使用的模型；项目大致规模（代码量、语言）；这个项目用 MP 跑了多久。
0.2 到现在为止有多少个 mission，其中多少已关闭；当前是常驻 Secretary 模式还是 4.2 模式；Secretary 换过几代，每次为什么换。

## 1. 规模和节奏
★1.1 选一个已完成或进展最多的 mission：派发总数是多少，按席位种类各多少；返工次数最多的任务返工了几次。
1.2 同时在途的席位最多有几个？是什么限制了并行（写路径重叠、harness 的子代理上限，还是别的）？
1.3 一次派发从认领到交回，典型时长和最长时长各是多少？交回时的验证运行一般跑多久？

## 2. Secretary 的裁决
★2.1 该 mission 里 Secretary 一共做了多少次裁决？请按升级来源分类计数（loop-exhausted、reviewer-needs-decision、exploration-direction 等）。
★2.2 相邻两次裁决之间的时间间隔：最短、典型、最长各是多少。
★2.3 抽 3 张真实的裁决 card：card 本身和每份必读材料各有多少字符。
★2.4 有没有哪次裁决，card 和必读材料不够用，要靠 Secretary 记得的现场情况、或你另外告诉它的话才能判断对？请举具体例子，或明确说没有遇到。
★2.5 这个项目在 4.2 模式（每次升级新起一个一次性 Secretary）下跑过吗？和常驻相比，裁决质量有没有你能具体说出的差别？
2.6 有没有前后矛盾的裁决，或者同一类失败被反复"再给一次"而没有换思路的情况？
2.7 转到你收件箱的 PM 级决定有多少条？其中多少问了用户，多少是"没有原话依据、影响小"由你自己定的？
2.8 你给 Secretary 发过多少条 note？有没有 note 在被确认之后还需要再看、却找不到的情况？

## 3. 原话的记录和分类
★3.1 到现在记录了多少条原话（W-n）、多少个标签？principle、decision、requirement、instruction 各多少？判为"无关"而没有记录的消息大约占多少？
★3.2 你对消息类型的判断，被用户提出异议过几次？事后 retag 过几次？最典型的判错是哪一类错成哪一类？
★3.3 "下一条消息没有异议才记录"这条规则，有没有让你在当轮想引用原话却不能引用？多久发生一次，你是怎么处理的？
3.4 一条消息含多种内容（比如既有需求又有指令）的情况多不多？用引文拆分标签时，最麻烦的是什么？
3.5 发生过几次"新话取代旧话"？逐项决定撤回还是保留时，哪一步最费劲？
3.6 粗略估计：你的上下文里，花在判断类型、记录、确认和打标签上的部分占多少？花在理解用户意图和计划上的占多少？
3.7 第一层（layer 1）有没有触到 8 KiB 上限？写过 summary 吗？

## 4. 停止
★4.1 一共发生过几次停止？每次停止时有多少席位在途？
★4.2 这些在途席位最后怎样了：等到停止解除后继续并交回，被 release --ended（已做的工作丢失），还是别的？丢掉的工作量大概多大？
4.3 从用户说"停"到所有席位确认结束，用了多久？有没有席位长期停在"未确认"？
4.4 停止之后用户通常怎么收场：原样继续、改计划，还是放弃？

## 5. 席位的行为
★5.1 交回被拒绝过多少次？主要原因是什么（写到写路径之外、必读材料没读完、JSON 字段不合格等）？
★5.2 席位没有交回就结束（WI-28）发生过几次？知道原因吗？
5.3 有没有席位做了角色不允许的事：运行 `mp pm` 或 `mp read`，动了别的任务的文件，自己提交或切分支，跑了完整测试套件？是怎么发现的？
5.4 Reviewer 把 Constructor 的产出打回的比例大概是多少？有没有 Reviewer 放过了问题、后来才暴露的例子？

## 6. 异常和长时间运行
6.1 实际触发过哪些 WI 页面，各几次？哪些只是照着敲命令，哪些真的需要判断？
6.2 有没有后台（detached）实验运行？最长跑了多久？有没有被停止或丢失（lost）的？
6.3 完整测试套件（full suite）跑一次要多久？一个 mission 里跑了几次？
6.4 常驻 Secretary 的启动、唤醒和停止，在你的 harness 上出过什么问题？

## 7. 模型
7.1 不同席位用过不同的模型或不同家族的模型吗？哪个席位对模型能力最敏感？
7.2 有没有"换一个模型来审，就发现了原模型没发现的问题"的例子？

## 8. 用户最常问什么
★8.1 用户最常问你的进度问题是哪几种？你分别用哪些命令回答？哪一类最难答清楚？
8.2 有没有什么信息，用户反复想看，而现有的命令行输出很难展示？

## 9. 开放题
★9.1 按浪费的时间或 token 排序，现在这套流程里最大的三个浪费是什么？
★9.2 手册里哪三条规则你最难做到、最容易忘，或者觉得和实际情况不符？
9.3 PM 会话或 Secretary 会话发生过上下文压缩或会话丢失吗？之后丢了什么，怎么恢复的？
9.4 如果只能改一处，你最希望改什么？
````

## 问卷二：复审返工原因调查

- **用途。** 查清复审为什么大多判返工。第一份问卷只给了比例（64% 返工，40% 的接受是带风险接受），没有给原因。
- **怎么用。** 整段贴给现场的 PM 会话。全部可以在 `memory.db` 的只读副本上用 SELECT 回答，不需要 Secretary。不能机械统计的题用 20 条随机抽样。
- **上次的回答。** 2026-11-27，由同一个项目的 PM 会话回答，同样在只读副本上做，没有问 Secretary。第 2 题另外用了只读的 `git diff --name-only` 来比对前后两次尝试的候选提交。

````md
# 复审返工原因调查（只读）

这是一次性的调查，用来指导 Mission Pipeline 4.4 的设计，与本项目的需求无关。

## 回答方式
- 只读，在 memory.db 的副本上做 SELECT，不运行任何会写入的 mp 命令。
- 每题给数字，并写明用的查询。无法机械统计的，抽样 20 个并说明是抽样。
- 没有数据就写"没有数据"。

## 问题
1. 返工的直接原因。392 次复审里判为 rework 的 250 次，各属于哪一类：
   (a) 交回时的程序验证就没通过；
   (b) 验证通过，但 Reviewer 判定有必须项没满足；
   (c) 验证通过，必须项都满足，Reviewer 提了标准之外的问题。
2. 后几轮的问题从哪来。对返工两次以上的任务，第二轮和之后各轮提出的问题里：
   (a) 上一轮就提过、没修好的，占多少；
   (b) 上一轮没提过、落在这次返工改动的代码上的，占多少；
   (c) 上一轮没提过、落在第一轮就存在且没动过的代码上的，占多少。
3. 标准数量和返工的关系。按任务的验收标准条数分组（1-3 条、4-7 条、8 条以上），各组的平均复审轮数和带风险接受的比例。
4. 按任务类型（interface / implementation / integration / experiment）分别统计返工率和带风险接受的比例。
5. 按模型统计。Reviewer 先后用过三个模型，各自的 rework 比例是多少？Constructor 如果换过模型，同样统计。
6. 只能实机验证的问题。被判 rework 或被带风险接受的项里，有多少是离线无法判断、只有在模拟器里才能确认的？
7. 带风险接受时留下了什么。66 次带风险接受里，留下的未满足项是必须项还是非必须项？后来各自怎样了：由修复解决、仍未解决、还是被放弃？
8. "已推迟的复审问题"通知有 233 条。这些被推迟的问题后来有多少被处理了，在哪里处理的？
9. 最费轮次的 5 条线，每条用三四句话说明它为什么反复。
````

说明：这一份里的具体数字（392、250、66、233）和"三个模型""模拟器"都来自第一份问卷的答复。换一个项目用的时候，要先把这些数字和说法换成那个项目的。

## 作为验收量具

4.4 的草稿（`handoff/drafts/DesignDoc_InformationFlow_4.4_2026-11-27_v01.md` 第 11 节）把这两份问卷定为验收的办法：新版本在真实项目上跑一段时间后，把同样的问题再问一遍，逐项和 `04-field-data.md` 里的数字对比。

值得逐项对比的数字，以及上次的值：

| 看什么 | 上次（4.3.0） | 4.4 想要的方向 |
|---|---|---|
| 一张裁决 card 的字符数 | 30 万到 34 万，约八成是无关约束 | 典型的 Constructor card 在 64 KiB 以内 |
| 一次裁决的必读材料页数 | 26 到 30 页 | 四页以内 |
| 约束的个数和版本数 | 169 个，354 个版本 | PM 不再用全项目约束承载单个任务的裁定 |
| card 过时导致没开工就撤回 | 11 次 | 接近 0 |
| Constructor 的提问（constructor-decision） | 177 次 | 明显减少 |
| Secretary 裁决里"问 PM"的比例 | 41% | 下降 |
| `mp sec next` 单次耗时 | 2.5 到 7 分钟（本地修复后约 50 秒） | 更短，且不随历史增长 |
| 有席位在跑时只有 1 个在途的时间占比 | 59% | 下降 |
| 复审判返工的比例 | 64% | 下降 |
| 接受里带风险接受的比例 | 40% | 下降 |
| 因 Reviewer 无法核实而反复 unclear 的标准 | 至少 33 条，分布在 12 个任务 | 不再触发返工 |
| Reviewer 的交回被拒 | 74 次，多数是引用了快照之外的证据 | 明显减少 |
| 带风险接受时留下的项，能否查到后来在哪处理 | 不能，记录里没有链接 | 能，逐条有负责人和状态 |
| 被推迟的复审问题里记为已修复的 | 87 个里 0 个 | 修了的能被记录为修了 |
| PM 和 Secretary 在记忆之外的私人笔记 | 83 KB 和 834 KB | 明显变小，剩下的内容能说清是什么 |
| 按需求条目回答进度 | PM 手工从笔记里拼 | 一条读取命令给出 |
| 换 Reviewer 模型后通过率的变化 | 从约一半降到 132 次里 2 次，没人看得出 | 有读取命令和通知能看出 |

再问的时候要注意：
- 条件尽量一致：同样在只读副本上做，同样区分【记录】和【印象】。
- 第二份问卷里写死的数字要先换成当时的数字。
- 模型、任务难度和项目阶段都会变，单看一个数字的升降不能直接归因于版本。上次 Reviewer 换模型的那组数据就是一个例子。
